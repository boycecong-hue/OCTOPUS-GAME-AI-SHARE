## 1. 背景

当前 `sections/03-cli.md` 已经具备“为什么 CLI / Agent 是主战场”这一章的核心框架，但在 `Claude Code / Codex / Gemini` 的对比部分，现有内容更接近产品介绍与优势罗列，还没有把三者的**架构路线差异**明确讲透。

本次设计的目标不是单纯补充资料，而是把这一页升级为一段更适合演讲的论证：

- 让听众理解主战场为何从“补全”转向“任务闭环执行”
- 让听众理解三家都在做 agent，但路线不同
- 让一线工程师听完后获得一个可复用的判断框架

## 2. 设计目标

这一页需要同时完成五个目标：

1. 承接前文“CLI 比 IDE 更适合 Agent”的论证
2. 解释为什么今天比较 AI Coding 工具，不能只比较模型能力
3. 用统一架构视角解释 Claude Code、Codex、Gemini 的不同产品路线
4. 让每条路线都能落到一个“具体是怎么工作的”机制级例子
5. 给工程师一个简洁、可复述的理解与选型框架

## 3. 目标听众

默认听众是一线工程师。

因此内容取舍需要遵守以下原则：

- 优先讲清工作方式变化，而不是企业采购视角
- 优先讲清产品架构路线，而不是罗列全部功能
- 每一条路线至少要配一个“机制 + 例子”，避免停留在抽象判断
- 语言要适合演讲口播，避免写成研究报告或参数表
- 结论必须能帮助工程师快速建立心智模型

## 4. 核心立论

这一页的核心立论是：

> Claude Code、Codex、Gemini 不是简单的强弱关系，而是在 AI Coding Agent 时代选择了不同的产品架构路线。

配套的辅助立论如下：

- 上一代竞争重点是“谁补全得更快更准”
- 这一代竞争重点是“谁更能把需求变成可执行、可验证、可交付的任务闭环”
- 因此，比较对象不再只是模型，而是整套开发代理系统

## 6. 详细内容设计

### 6.1 开场段

开场段负责把讨论焦点从“功能比较”切换到“架构路线比较”。

建议文案方向：

- 上一代 AI Coding 更像编辑器增强
- 这一代 AI Coding 更像开发任务执行系统
- 所以比较三家时，不能只看模型能力或代码生成能力

建议核心句：

> 今天比较 Claude Code、Codex、Gemini，不能只看谁更会写代码，而要看它们各自把主战场放在了哪一层。

### 6.2 通用架构总图

在正式进入三家对比前，先给出一张通用 AI Coding Agent 四层图，用于统一分析框架。

四层分别是：

1. **交互表面层**：CLI / IDE / Web / Cloud
2. **执行编排层**：任务拆解、工具调用、验证修复、并行代理
3. **上下文接入层**：代码库、终端、文档、浏览器、外部系统
4. **生态落地层**：团队规范、云平台、权限治理、自动化流程

这张图的核心作用有两个：

- 告诉听众三家都不是“一个聊天框”，而是一套 agent 系统
- 给后面的三方对比提供统一坐标系

建议图下解释语气保持极简：

- 三家都在做 agent
- 差异不在于会不会写代码
- 差异在于产品重心压在哪一层

### 6.3 三家路线表

对比方式从“能力清单”改为“架构路线表”。

推荐比较维度如下：

- 主战场压在哪
- 核心产品思路
- 代表性能力组织方式
- 一个最能说明路线差异的具体例子
- 更适合解决的问题
- 一句话理解

推荐表述方向：

#### Claude Code

- 主战场：执行编排
- 产品思路：把 agent 做成可编排开发系统
- 代表能力组织：Skills / Hooks / MCP / Subagents
- 具体例子：把 code review 封成专门子代理，主代理完成实现后自动委派 reviewer；再通过 hooks 在关键节点拦截危险操作，或在子代理结束后自动汇总结果；如果需要外部信息，再通过 MCP 接 GitHub、文档或内部系统
- 更适合：流程闭环、规范沉淀、团队复用
- 一句话理解：可编排代理系统

#### Codex

- 主战场：多表面统一入口
- 产品思路：把 coding agent 覆盖到 CLI / IDE / Cloud
- 代表能力组织：CLI + IDE + cloud tasks + parallel environments
- 具体例子：开发者在本地 CLI 或 IDE 提交一个修 bug 任务，Codex 把任务丢到云端独立环境执行，拉仓库、跑命令、改代码、产出 diff 与日志；如果同时有多个任务，可以分配到多个并行环境分别处理，最后统一回到用户面前审阅
- 更适合：跨环境一致体验、远程执行、任务分发
- 一句话理解：统一 coding agent 产品面

#### Gemini

- 主战场：Google 生态联动
- 产品思路：把 coding agent 嵌进 IDE + Cloud + Google 工具链
- 代表能力组织：Gemini CLI + Gemini Code Assist + Google Cloud
- 具体例子：Gemini CLI 可直接运行在 Cloud Shell 中，不需要额外搭环境；这样 agent 进入点就在云端终端里，天然拿到 GCP 身份与项目上下文。另一类例子是 Gemini Code Assist 直接出现在 Google Cloud 产品中，例如在 BigQuery Studio 基于表元数据生成 query 或 data insights，或者在 Apigee 里用自然语言创建和编辑 OpenAPI 规范
- 更适合：长上下文理解、云上开发、Google 生态协同
- 一句话理解：生态驱动的 coding agent

### 6.4 机制级口播解释

表格后增加三条极短解释，帮助讲者从“表格信息”切换到“口头理解”：

- Claude Code 的重点不是“一个入口”，而是“怎样把技能、规则、工具和分工编排成稳定工作流”。
- Codex 的重点不是“本地 CLI 本身”，而是“同一个 agent 如何覆盖本地、IDE、云端任务和并行环境”。
- Gemini 的重点不是“单独一个 CLI”，而是“把 agent 植入 Google 的 IDE、Cloud 与产品界面，让云上下文直接参与工作”。

### 6.5 演讲中的示例展开方式

为了避免页面只停留在抽象总结，讲者在表格之后需要立刻举一个“机制级例子”。建议每家只讲一个最典型的例子：

- **Claude Code 示例讲法**：不是说“它有 Skills、Hooks、MCP”，而是说“你可以把 code review 做成一个专职子代理，写完代码后自动调用 reviewer，再用 hook 拦截危险命令，最后再通过 MCP 去拿 GitHub issue 或内部文档”。这样听众会理解 Claude Code 的强项是编排能力。
- **Codex 示例讲法**：不是说“它支持 cloud tasks”，而是说“你在本地提一个 bug 修复任务，真正执行发生在云端独立环境里；如果有三个任务，可以扔给三个并行环境同时做，最后你回来统一审结果”。这样听众会理解 Codex 的强项是统一入口和云端异步执行。
- **Gemini 示例讲法**：不是说“它和 Google Cloud 集成得好”，而是说“Gemini CLI 可以直接在 Cloud Shell 里跑，这意味着 agent 一开始就站在云端环境里；另一边 Gemini Code Assist 还能直接出现在 BigQuery Studio 或 Apigee 这样的云产品里，直接利用数据表元数据、API 规范这些云侧上下文”。这样听众会理解 Gemini 的强项是把 agent 嵌进云控制面与产品工作流。

### 6.6 工程师判断框架

这一页结尾不能只做总结，还要给听众留下判断框架。

建议用三条“如果你更看重什么”来收尾：

- 如果更看重任务闭环、流程编排、团队沉淀，更容易被 Claude Code 打动
- 如果更看重统一入口、多执行表面、云端任务协同，Codex 更顺手
- 如果更看重 IDE + Cloud + Google 生态协同，Gemini 更自然

最后补一个总收束：

> 三家都在做 Agent，但 Claude Code 更像编排系统，Codex 更像统一入口，Gemini 更像生态联动层。
